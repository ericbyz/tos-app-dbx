# TOS 应用自动化构建与部署流程报告

> 项目：tos-app-dbx（将开源数据库客户端 [DBX](https://github.com/t8y2/dbx) 封装为 TOS 应用）
> 实测环境：TOS 7.0.1536（VMware Workstation 26.0.1 虚拟机）
> 报告日期：2026-11-16
> 结论先行：**悬浮窗口方案已全部打通** —— 应用中心正规安装 + `iframe` 内嵌模式 + nginx conf.d 路由 + `exec: false`

---

## 一、最终形态（为什么这样设计）

| 决策点 | 选型 | 理由 |
|---|---|---|
| 应用类型 | `application_type: "deb"`（单包） | 上游 dbx-web 是 musl 静态二进制，无需打包依赖，双架构通用 |
| 窗口模式 | `"type": "iframe"` + `"path": "/dbx/"` | 悬浮在 TOS 主桌面内（用户要求），不跳新标签页 |
| 前端来源 | 上游内嵌（无 webui.bz2） | dbx-web 前端已内嵌在二进制中，无需打包静态页 |
| 后端通道 | **端口模式**（TCP 18224） | dbx-web 不支持 Unix socket；nginx `proxy_pass` 到本机端口 |
| 基路径 | `DBX_PUBLIC_BASE_PATH=/dbx` | dbx-web 原生支持反代子路径，iframe 嵌入必备 |
| `exec` 字段 | **`false`（关键！）** | `true` 会走 TOS SPA 的"启动后端"分支，在该 beta 上静默失败 → 窗口空白 |
| 数据目录 | `/var/lib/dbx` | systemd `ReadWritePaths` 白名单内，卸载可 purge |

> ⚠️ **`exec: false` 是整个悬浮效果能否成立的最关键配置**。上游 deb 里 `exec: true` 表示"有后端程序"，TOS 桌面对 `exec: true` 的 iframe 应用会走"启动后端→就绪→加载窗口"分支，该分支在 TOS 7.0 beta 上静默失败（窗口空白）。置为 `false` 后走纯 iframe 渲染分支，与系统应用"文本编辑器"同路径（已验证可用）。

## 二、包结构（全部文件及职责）

```
tos-app-dbx/
├── config.ini              # 平台元数据（JSON）：id=dbx, type=iframe, path=/dbx/, exec=false
├── dbx.lang                # 26 种语言名称/描述（生成：scripts/make_lang.py）
├── dbx.env                 # 服务环境变量：DBX_PORT=18224, DBX_PUBLIC_BASE_PATH=/dbx,
│                           #   DBX_PACKAGE_ROOT=/usr/local/dbx, DBX_DATA_DIR=/var/lib/dbx
├── UPSTREAM                # 上游锁定：版本 tag、资产名、SHA256（可复现构建的凭证）
├── DEBIAN/
│   ├── control             # Package: dbx; Architecture: amd64|arm64; Depends: systemd
│   ├── postinst            # 建用户/目录 → enable+start 服务（平台安装时也会调用）
│   ├── prerm / postrm      # 停服务 / purge 清理（用户、数据、服务单元）
├── init.d/dbx.service      # systemd 单元（NoNewPrivileges/ProtectSystem 等加固，
│                           #   无 Restart=——平台管理生命周期）
├── images/icons/dbx.svg    # 应用图标（SVG, viewBox 0 0 512 512, 透明背景）
├── nginx/dbx.conf          # ⭐ 悬浮路由核心：location /dbx/ → proxy_pass 127.0.0.1:18224
│                           #   （不带尾斜杠，保留 /dbx 前缀；client_max_body_size 512m）
├── scripts/
│   ├── fetch_upstream.sh   # 下载上游 browser-static 资产 + SHA256 强校验
│   ├── build_deb.py        # 纯 Python dpkg-deb 兼容打包器（Windows/CI 通用，确定性构建）
│   ├── validate.py         # TOS 审核规则校验（字段/互斥/语言覆盖/图标/路由一致性）
│   ├── make_lang.py        # 生成 26 语言 lang 文件
│   └── bump_upstream.sh    # 上游升级（UPSTREAM/config.ini/control 三处联动）
├── build.sh                # 一键构建：parse UPSTREAM → fetch → stage → dpkg-deb/build_deb.py
└── .github/workflows/
    ├── validate.yml        # 每次 push：元数据校验 + 上游锁定一致性
    └── build-deb.yml       # tag v*：双架构矩阵构建 → lintian → SHA256 → Release
```

                bin/dbx-web-bin, init.d/dbx.service, images/icons/dbx.svg}

## 三、构建流程

### 3.1 上游资产（免编译）

上游每次发布提供 `DBX_<ver>_x64-browser-static.tar.gz`（Linux x86_64）与
`DBX_<ver>_arm64-browser-static.tar.gz`（arm64），内含 musl 静态二进制 `bin/dbx-web-bin`
（无 ELF 解释器、无 DT_NEEDED，任意 glibc 版本可用）——**不需要交叉编译**。

> ⚠️ 上游命名陷阱：`dbx-web_<ver>_x86_64-browser-static.zip` 是 **Windows** 版；
> Linux x86_64 的资产名是 `DBX_<ver>_x64-browser-static.tar.gz`。

### 3.2 本地构建

```bash
cd Z:\business\company\twm\tos-app-dbx
python scripts/validate.py     # 审核规则预检
bash build.sh                  # 双架构（有 dpkg-deb 用之，否则 build_deb.py）
# 产物：build/output/dbx_x86_64.deb + dbx_aarch64.deb + 各自 .sha256
```

### 3.3 CI 构建（GitHub Actions）

- 触发：`git tag v<上游版本> && git push origin main <tag>`
- 矩阵：`[x86_64, aarch64]` 两 job 并行（纯打包无需 QEMU）
- 步骤：checkout → apt 装 dpkg-dev/lintian → `bash build.sh <arch>` →
  `dpkg-deb -I/-c` + `lintian --fail-on error`（豁免 `dir/file-in-usr-local`、
  `embedded-library`、`statically-linked-binary`——分别为 TOS 结构要求与上游二进制固有特征）
  → SHA256 → Release 发布（需 `permissions: contents: write`）

### 3.4 升级上游版本

```bash
./scripts/bump_upstream.sh <new-version>   # 联动改 UPSTREAM/config.ini/control
# 手动把新 Release 的两个 .sha256 值填入 UPSTREAM
./build.sh && ./scripts/validate.py
git commit -m "bump upstream" && git tag v<new-version> && git push origin main <tag>
```

## 四、安装流程（应用中心正规路径 —— 必须遵守）

> 直接 `dpkg -i` 会缺失平台接线（nginx 路由、应用注册），导致悬浮窗口无法打开。
> 平台安装才会完成：解包 → **生成/接线 nginx 路由** → 写应用注册 → 服务管理。

### 前置条件

1. **存储池已创建**（应用中心/文件管理依赖；无池时手动安装向导显示 `no_valid_data`）
2. 安装包位于 TOS 可浏览的文件空间（如 `Volume1 > homes > twmtest` 或 `Public` 共享）

### 操作步骤（应用中心 UI）

1. **文件管理** → 上传 `dbx_x86_64.deb`（从电脑拖入，或先经其它通道放入共享）
2. **应用中心** → 右上角第 1 个图标（手动安装向导）→ 四步流程：
   - ① 选择位置：**Volume 1**
   - ② 选择安装包：「从 TNAS 上传」→ 浏览到 homes/twmtest → 选 deb
   - ③ 确认信息（平台解析 config.ini 显示应用名/图标/版本）
   - ④ 开始安装 → 进度 100% → 安装完成
3. 安装完成后应用出现在「已安装」列表（状态：已启用）

### 平台安装自动完成的事项（对比 raw dpkg 的差异）

| 事项 | 平台安装 | raw dpkg |
|---|---|---|
| 解包到 /usr/local/dbx/ | ✓ | ✓ |
| 应用注册（/v2/app/list 可见） | ✓ | ✗ 需手动放 system_app_data |
| nginx 路由生成/接线 | ✓（按安装时注册的类型） | ✗ 需手动放 conf.d + reload |
| 服务启动 | ✓ | ✓（postinst） |

## 五、悬浮窗口的三块拼图（缺一即白屏/打不开）

1. **注册配置 = iframe 模式**：`/usr/local/system_app_data/dbx/config.ini` 的
   `type`/`path` 必须是 `iframe`/`/dbx/`（平台按此生成窗口与路由）。
   安装包里的 config.ini 会被平台复制到该位置；**若该位置已有旧文件则不会被覆盖**
   ——升级模式时务必核对（本次实战曾因旧注册未同步导致窗口空白）。
2. **nginx 路由生效**：`/dbx/` → `127.0.0.1:18224`。平台对第三方 iframe 应用按
   安装时注册的类型生成路由；若类型事后变更（如外开→iframe），需手动补：
   ```bash
   cp /usr/local/dbx/nginx/dbx.conf /etc/nginx/conf.d/ && nginx -s reload
   ```
   （/etc/nginx/nginx.conf 第 41 行 `include conf.d/*.conf;` 已验证生效且持久）
3. **`exec: false`**：见第一节。用
   `sed -i 's/"exec": true/"exec": false/' /usr/local/dbx/config.ini /usr/local/system_app_data/dbx/config.ini && systemctl restart dbx`
   修复后需刷新桌面（SPA 重新拉取 /v2/app/list）。

## 七、故障排查速查

| 症状 | 根因 | 处理 |
|---|---|---|
| 窗口空白 | `exec: true` 走坏分支 | sed 改 `exec: false` + 重启服务 + F5 |
| 窗口空白 | 注册配置仍旧模式 | `cp /usr/local/dbx/config.ini /usr/local/system_app_data/dbx/` + F5 |
| 点图标无反应 | SPA 内存配置过期 | F5 刷新桌面再点 |
| `/dbx/` 404 | nginx 路由未接线 | `cp .../nginx/dbx.conf /etc/nginx/conf.d/ && nginx -s reload` |
| :18224 拒绝连接 | 服务未启动 | `systemctl enable --now dbx` |
| :18224 根路径 404 | 正常 | 探测 `/dbx/` 路径（基路径模式） |
| 手动安装下拉空 | 无存储池 | 存储管理创建存储池 + 卷 |
| 终端输入无效 | ttyd ws 会话死亡（页面刷新后） | 关闭终端窗口重开（新 ws），或 F5 |
| 终端命令不执行 | 发的是 `\n`（LF） | 发 `\r`（CR）或用 keypress Enter |
| 登录互踢 | TOS 单会话限制 | 自动化与人工不要同时登录 |
